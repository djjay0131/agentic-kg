# ADR-0007: Secrets are machine-generated, machine-stored and never seen

Status: Accepted
Date: 2026-10-09

## Context

The owner set a standing rule (2026-10-09): *all key generation and rotation
is done by an automated process — a GitHub or GCP workflow — that generates
the key, stores it, and never sees it.* No person and no agent (Claude,
OpenCode workers, reviewers) ever handles a secret value.

An audit of `.github/workflows/` and `infra/` on 2026-10-09 found:

| Secret | Origin | Where it lives | Gap against the rule |
|---|---|---|---|
| `NEO4J_PASSWORD` | Generated by `rotate-neo4j-password.yml` (ADR-0006) | Secret Manager | Generated on a GitHub runner (masked) and streamed runner → Secret Manager; it should never leave GCP |
| `SEMANTIC_SCHOLAR_API_KEY` | Issued by Semantic Scholar | GitHub secret (source of truth) → Secret Manager via `sync-s2-key.yml` | Vendor-issued; two copies; the GitHub copy is entered by a person |
| `OPENAI_API_KEY` | Issued by OpenAI | GitHub secret and Secret Manager | Vendor-issued; two copies |
| `ANTHROPIC_API_KEY` | Issued by Anthropic | Secret Manager (API service, ingest Job, `cloudbuild.yaml`) | Vendor-issued; already single-homed — needs only the value-free roll |
| `CODECOV_TOKEN` | Issued by Codecov | GitHub secret | Avoidable: Codecov accepts GitHub OIDC |
| `GCP_WORKLOAD_IDENTITY_PROVIDER` / `GCP_SERVICE_ACCOUNT` | Resource names, not credentials | GitHub secrets | None — auth is keyless (WIF) |

## Decision

1. **Keyless first.** Where the other side accepts federated identity, no
   secret exists: GitHub → GCP uses Workload Identity Federation; Codecov
   uploads use GitHub OIDC (`use_oidc`). New integrations must use OIDC/WIF
   when the provider supports it.
2. **Generated secrets are generated where they are used.** A secret we
   control (database passwords, signing keys, HMAC keys) is generated inside
   GCP by the job that installs it, written straight to Secret Manager, and
   never transits a GitHub runner, a log, an artifact, a workflow output or a
   step summary. The orchestrating workflow only triggers jobs and manages
   secret *version metadata* (enable / disable / destroy); it never reads a
   value. Rotation is scheduled, not remembered.
3. **Vendor-issued keys have exactly one home: Secret Manager.** Keys a vendor
   issues (Semantic Scholar, OpenAI) cannot be generated by a workflow. The
   owner adds each new version once, directly in Secret Manager (console or
   `gcloud secrets versions add --data-file=-` on his own machine). Workflows
   that need the key fetch it at run time through WIF
   (`google-github-actions/get-secretmanager-secrets`), masked; Cloud Run
   reads it via `secret_key_ref`. There is no GitHub-secret copy and no
   "sync" step that copies a value between stores. A workflow rolls services
   onto the newest version and disables superseded versions without reading
   any value.
4. **Agents never handle values.** Agents may write workflows, Terraform and
   code that *move* secrets between machine stores, and may dispatch those
   workflows; they never print, read, paste, echo or store a secret value,
   and never ask a person to send one through chat, a PR or an issue.
5. **Verification is by effect, not by value.** A rotation proves itself by a
   health check that exercises the new credential (e.g. the API reports
   `neo4j_connected`), never by displaying or comparing the value.

## Rationale

Every place a secret value appears — a runner's memory, a log, a chat, a
second store — is a place it can leak, and each copy is one more thing to
rotate. Generating in the consuming environment and keeping one store per
secret minimises both.

## Alternatives Considered

### Keep GitHub secrets as the source of truth for vendor keys

Simple, but keeps two copies and a copy step that reads the value on a runner.

### Generate on the GitHub runner, masked (ADR-0006 as first built)

Never shown to a person, but the value still leaves GCP; rule 2 removes that.

## Consequences

### Positive

- No secret value ever reaches GitHub for generated secrets; one store each.
- Codecov needs no secret at all.

### Negative / Tradeoffs

- The owner enters vendor keys in the GCP console instead of GitHub settings.
- Jobs that rotate need a dedicated service account with narrow
  `secretVersionAdder` grants (Terraform).

### Risks

- The deploy/apply identity `gh-deploy` holds `roles/secretmanager.admin`
  (needed for Terraform apply), so it can technically read secret values and
  add versions. Workflows running as it must never call `versions access`;
  narrowing it (split apply vs deploy identities) is follow-up work.
- Vendor keys cannot rotate themselves; their rotation cadence depends on the
  vendor. A reminder, not a value, is the most automation can do.
